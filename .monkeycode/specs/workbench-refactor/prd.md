## 1. 背景与问题

### 1.1 产品现状（GitHub main v1.3.1 核验版）

AgentTeams Dashboard 是上游 **AgentTeams（多智能体协作运行时）的 Mission Control**：一个 Next.js 16 控制台，用于督导 Worker / Team / Manager / Human，提供带人工干预（HITL）的任务看板、可感知运行时的 Matrix 聊天、RBAC/审计治理与 AI 诊断。浏览器从不直连后端，全部经 Next.js API Route 代理（`docs/ARCHITECTURE.md:7`）。

**事实一：它是一个单页 SPA，不是一个多页面控制台。**
`src/app` 只有 2 个真实页面：`/`（登录/首启/主控制台三态）与 `/replay/[id]`（只读回放）。13 个「页面」是同一页内的 section 组件，由 `activeSection` 状态切换（`src/components/dashboard/agent-teams-dashboard.tsx:54-82`），URL 只记录扁平 hash（`#chat`/`#workers`/`#coding-runs`），默认落地 **聊天**（`use-active-section.ts:55-61,102-105`）。

**事实二：一级导航是 3 组 13 项，不是 18 项平铺。**
`nav-items.ts:42-70`（GitHub main / v1.3.1）定义：基础（总览、聊天）/ 运行时（任务看板、产物、**编码执行**、Workers、Managers、团队、Humans）/ 资源中心（市场、模型、知识库、审计）。插件可动态追加侧栏入口（内置 2 项：问天诊断、监控面板），顶栏另有 4 个快捷动作（`nav-items.ts:110-115`）。前稿的「18 个模块」是把 v1.3.0 时期的 12 个导航项 + 2 个插件项 + 4 个顶栏动作相加，且未计 v1.3.1 新增的「编码执行」。

**事实三：能复用的底子已经很厚。**

| 能力域 | 现状（可复用资产） |
| --- | --- |
| Matrix 聊天 | 虚拟化时间线、线程、未读分隔线、per-room 草稿、邀请收件箱、乐观发送重试、13 条优先级消息分派、8 类块渲染器（A2UI、AgentScope repr、`org.agentteams.run` v1、Tool Guard 确认、`agentteams.workflow`、Hermes、旧卡片、纯文本） |
| 项目/任务 | 项目 5 态、DAG/loop 只读展示、workflow 拓扑 SVG、事件流分页（≤2000 条）、暂停/恢复/重规划/取消任务 4 个干预写、干预历史快照；看板由 MinIO meta + Matrix 工作流事件 + Controller workflow 三源合并 |
| 交付物 | 项目→任务→文件树、按类型分类、内联预览（**前端 1MB 硬常量**）、下载走 Controller 流式代理（服务端无大小限制） |
| 编码执行（v1.3.1 新增） | 「编码执行」只读 section：`GET /api/agentteams/coding-runs` 列表（≤200，v2 元数据来自上游 `runs.jsonl`）+ 详情原始日志 / `?format=json` 结构化信封；Worker 详情新增「编码 CLI」管理面板（`qwen-code` / `opencode` / `qoder`，含 6 个场景 preset、安装轮询、settings 脱敏） |
| 治理 | 双轨登录（Higress Console 管理员 / Matrix 账号）、三级权限 + 显式规则 deny 优先、worker/team 作用域 RBAC、append-only JSONL 审计（10MB × 30）、SSRF 白名单、PII 脱敏、敏感文件过滤 |
| 扩展 | 插件 5 类扩展点（侧栏/独立页/仪表盘组件/详情区块/工具栏）、主题 32 色 + 11 布局效果参数、企业 `theme.config.json` 下发 |
| 工程 | **246 个测试文件**（178 `.test.ts` + 68 `.test.tsx`，GitHub main 树统计）、`tsc` 严格模式、ESLint 0 错误门、CI 四流水线（lint/typecheck/test/docs-consistency）；v1.3.0 CHANGELOG 自述 234 files / 2160 tests |

**事实四：四个部署形态与无状态约束。**
同一镜像由环境变量决定形态：Standalone / Shared / Embedded / **Stateless**（`README.md:177-288`）。Stateless 是**零服务端存储**：浏览器持有自己的 Matrix token，服务端不落任何用户态；此时对象存储、网关管理、日志、Nacos、SGLang 探测、基础设施健康 **6 类路由直接 501**（`static-mode.ts:42-80`）。这条约束直接否决了前稿「循环/评论/审查报告落卷内 SQLite/JSONL」的方案。

### 1.2 六个结构性问题（替代前稿 P1–P5）

| 编号 | 问题 | 核验后的具体表现 |
| --- | --- | --- |
| **P1** | **主线割裂**：讨论、进度、干预、交付物分散在 4 个 section | 聊天里讨论、看板里看进度、产物里找文件、总览里处理 HITL；同一件事要换 4 个地方，深链最细只到 section（无 per-room / per-task URL） |
| **P2** | **编排只有「只读」，没有「资产」** | 项目 DAG/loop 是 Manager 用 `projectflow` 生成的，Dashboard 只能看拓扑与做 4 个干预动作；流程无法被人类作者化、版本化、复用 |
| **P3** | **人的介入被切成两个半成品** | 只有工具确认二态（批准/拒绝发回 Matrix），没有「执行中 Agent 提问 → 选项式答复 → 超时升级」；也没有「审查报告 → 派单 → 复测 → 放行」的终态闭环 |
| **P4** | **交付物不可协作** | 只是任务字段（`deliverables[]` / `result_path`），无实体、无版本、无状态机；无位置级评论、无意见批量派发；1MB 预览上限硬编码在前端两处常量（知识库单块 1MB 属另一套机制） |
| **P5** | **上手门槛高** | 首屏落在聊天但缺少「三步跑通」引导；Worker/Team/Manager/Human 四类概念先于用户目标出现；没有示例空间与示例循环 |
| **P6** | **事实漂移**（新增） | 版本号四处不一致（`package.json` 1.3.1 / README 中英 v1.2.4.9 / 安装脚本默认 v1.2.4.9 / 部署文档 v1.2.2）；导航、路由、测试数文档全面过期；上游契约无编译期保护，仅周检告警 |

### 1.3 行业信号：Teamily 的启示

Teamily 的实测案例（一份挂烫机资料 → 产品介绍页）验证了一个判断：**用户要的不是「管理 Agent 的控制台」，而是「和 Agent 一起干活的地方」**。其关键机制：人、Agent、成果同处一个群；协调者 Agent 自动拆解分派；成果以卡片回到对话流；审查报告 → 群内 @ 指令 → 修复 → 复测 → 放行；分工可沉淀为可视化「循环」，换素材复跑。

### 1.4 为什么是现在

- **可复用的底子已就位**：聊天渲染链、项目 workflow 读契约、Matrix 事件、审计与 RBAC 都已具备，增量做在「协作与资产层」，不是推倒重来；
- **但上游契约有硬缺口**：本仓没有「建群 / 建任务 / 建项目 / 发布循环」的写接口；v1.3.1 虽已消费编码执行记录 v2 读契约（`#150`/`#151`）与 Coding CLI 管理面（上游 `#1360`），但都是只读/配置向，不改变「执行写路径在上游」的事实。任何「一键发起 / 一键发布」都必须写成「依赖上游新契约 + 可验证降级」，否则上线即空承诺（详见 §8）；
- **范式已被验证，而治理/私有化/开放生态恰是我们的存量优势**：不要在 Teamily 的强项上硬碰，要把协作范式补上、把治理底座放大；
- **文档漂移已经开始咬人**：本 PRD 的两次前稿都建立在过期现状上，若不先钉住事实，重构会重复犯同样的错。

## 2. 标杆拆解与能力差距

### 2.1 Teamily 六大机制

| 机制 | 要点 | 对 Dashboard 的映射 |
| --- | --- | --- |
| 群聊即工作台 | Agent、真人、群聊并列；资料/讨论/产出都在同一对话流 | 已有 Matrix 房间 + 虚拟化时间线，缺「房间 = 工作单元」的定位与任务/交付物的一等绑定 |
| Agent 团队接力 | 协调者拆解 → 指派 → 明确依赖，用户只说做什么 | Manager 已具备协调者雏形（`projectflow` 生成 DAG/loop），缺「接力过程可视化 + 与对话绑定」 |
| 成果沉淀对话流 | 每个产出是可点开的卡片，可回溯 | 已有工件 chip / `agentteams.workflow` 卡，缺「工件卡 = 一等消息 + 三态」 |
| 审查-修改闭环 | 结构化报告 → 一句 @ → 修复 → 复测，默认终点是人 | 已有任务级结果（`result.md` 的 Outcome）与工具确认，缺报告/派单/复测/放行闭环 |
| 智能体循环 | 画布 + 条件退回 + 草稿/发布分离 + 复用 | **完全缺失**（只有只读 DAG/loop 视图） |
| 多人协同编辑 | 位置级评论 + 同编 + 意见批量派发 | 交互层完全缺失 |

### 2.2 能力对照（核验后修正）

| 能力维度 | Teamily | Dashboard 现状（v1.3.1） | 结论 |
| --- | --- | --- | --- |

| Agent 自动接力 | ✅ | ⚠️ Manager 可生成 DAG，但过程不可视、不可绑对话 | **主要差距** |
| 成果沉淀对话流 | ✅ 一等消息 | ⚠️ 有 chip/卡，无状态机/版本/评论 | 需升级 |

## 3. 目标与非目标

### 3.1 定位重塑

- **现在**：Mission Control for multi-agent teams —— 运维视角的集群控制台。
- **重构后**：**Collaborative Workbench** —— 人机协同工作台 + 完整治理底座。
- **一句话**：让人、Agent 和成果留在同一个地方；一件事在这里发起、讨论、修改、放行；流程沉淀为可复用的循环。

### 3.2 目标（G1–G6）

| 编号 | 目标 | 度量（发布后 1 个季度） |
| --- | --- | --- |
| **G1** | 协作动线贯通：发起 → 接力 → 审查 → 放行，全程不离开工作台 | 完整闭环的核心跳转次数 ≤ 2 次 |
| **G2** | 上手门槛降低 | 新用户从登录到发起第一个任务 ≤ 5 分钟（埋点 P50） |
| **G3** | 流程资产化（P1） | 内置 ≥5 个循环模板；循环复用率（同一循环发起 ≥2 次）≥ 30% |
| **G4** | 交付物协作闭环（P1） | 预览 → 评论 → 批量派发 → 修改确认 全链路可用 |
| **G5** | 治理不倒退 | 新增能力审计覆盖率 100%；RBAC 粒度不降；246 个测试文件基线全绿不回退 |
| **G6** | 事实一致（新增） | 文档漂移清单清零：版本号四处一致、导航/路由/测试数口径统一、上游契约变更 72h 内登记 |

> 北极星指标：**周活跃空间中「人发起 → Agent 接力 → 审查放行」完整闭环的完成次数**（基线取任务看板周完成任务数），目标环比 +200%。

### 3.3 非目标

1. **不做通用 IM**：不做音视频、朋友圈、社交关系链；
2. **不自研 Agent 运行时/执行引擎**：循环与任务执行仍由上游 Controller（项目/DAG/loop）承载，Dashboard 只做定义、发布、视图与复用；
3. **不做多租户 SaaS 化**：维持现有 4 种部署形态；
4. **不破坏生态兼容**：插件 5 类扩展点、主题参数、`org.agentteams.run` v1 消费全部向后兼容（**本期不新增第 6 类扩展点**，见 Q6）；
5. **不改变权限模型本身**：沿用三级 + worker/team 作用域，只做口径修正与 UI 门；
6. **P0 不做实时协同编辑**：评论 + 意见派发先行，MD 同编进 P2。

## 4. 用户与角色

### 4.1 三档角色（中性口径）

| 档位 | 能力 | 现有映射 | 重构后主界面 |
| --- | --- | --- | --- |
| **观察者** | 只读：看空间、看任务、看交付物 | Dashboard level 1；CRD level 3（Worker 档） | 工作台（只读态） |
| **协作者** | 参与空间、发消息、处理分配给自己的干预、提交审查意见 | Dashboard level 2；CRD level 2（团队成员） | 工作台 |
| **管理员** | 全部能力：资源配置、循环发布/回滚、安全策略、审计全量、热补丁 | Dashboard level 3；CRD level 1（管理员） | 工作台 + 控制台 |

> 映射关系是**反向**的：CRD 1→Dashboard 3、2→2、3→1（`dashboard-session.ts:202-207`、`rbac-engine.ts:16-31`）。完整映射与权限矩阵见附录 B。文档中不得再出现无映射说明的「L1/L2/L3」字样。

### 4.2 核心用户旅程

**旅程 A：新用户 5 分钟跑通第一个闭环**
登录（保留双地址 failover 与嵌入式预填）→ 进入示例空间 → 示例循环「产品介绍页生产线」绑到空间 → 发一条带素材的消息 → 看到接力卡流动 → 收到审查报告 → 点「放行」→ 工件卡变「已放行」。

**旅程 B：人机协作生产（对标 Teamily 挂烫机案例）**
协作者在空间上传商品资料并发起任务 → 协调 Agent（Manager）经 `projectflow` 生成 5 项子任务（架构 ∥ 视觉 → 设计 → 审查）→ **接力卡**在消息流呈现子任务、责任 Agent、依赖与实时状态 → 各 Agent 产出以**工件卡**回到时间线 → 审查 Agent 发**结构化审查报告**（2 阻断 / 2 建议）→ 协作者 @ 协调 Agent 下达修改指令（或对问题项批量派单）→ 修复 → 复测（不过再来一轮）→ 人工终审点「放行」→ 工件卡三态更新，全程落审计。

**旅程 C：循环资产化（P1）**
管理员把旅程 B 的分工「另存为循环」→ 画布微调节点与退回路由 → 存草稿 → 预演（干跑校验）→ 发布 → 换一份桌面风扇资料，从同一入口复跑 → 其他空间接入该已发布循环的一段。

**旅程 D：执行中干预（P0 回填）**
Agent 执行中阻塞并提问（「你希望泳道按什么维度划分？」）→ 消息流出现**干预卡**（单选 + 推荐项置顶 + 自由输入，互斥）→ 协作者点选提交 → 任务恢复 running → 超时未处理则置灰 expired、保持 blocked 并升级通知管理员。

**旅程 E：治理（不变的安全底线）**
审计流新增 `loop.*`、`review.*`、`comment.*`、`hitl.*` 事件；问天诊断照常；敏感文件过滤、SSRF 白名单、worker 作用域 RBAC 不变；Stateless 形态下新增能力自动降级而不是报错。

## 5. 总体方案

### 5.1 四大体验支柱

| 支柱 | 一句话 | 主要落点 |
| --- | --- | --- |
| **对话即工作** | 群聊不是模块，是工作单元本身 | F1 协作空间 |
| **接力即编排** | 说清做什么，系统安排谁来做 | F1.2 接力卡 + F5 循环 |

| **治理即底座** | 协作越顺，治理越要在线 | F7 控制台 + 审计/降级 |

### 5.2 信息架构（混合式：工作台主轴 + 控制台二级）

```
AgentTeams Dashboard v2.0
├─ 🏠 工作台 Workbench（默认落地，一级主线）
│   ├─ 协作空间      空间列表 / 对话流 / 接力卡 / 工件卡 / 审查报告 / 干预卡
```

**与现状的对应关系**：13 个现有导航项**零删减**，只做归属调整；6 个已下线但代码存活的孤儿 section（architecture / security / quickstart / runtime / projects / docs）在 M1 一并清理，不允许「以为还能用」。

### 5.3 可达性机制（弥补层级收敛）

| 机制 | 要求 |
| --- | --- |
| **命令面板**（Cmd/Ctrl+K） | 全局搜索并跳转：空间 / 房间 / 任务 / 项目 / 循环 / Worker / 团队 / 审计事件；现有实现只搜 4 类实体，需扩展（`command-palette.tsx:37-80`） |
| **角色自适应默认视图** | 观察者/协作者落地工作台；管理员落地工作台 + 控制台 pin；均可在设置中改默认 |
| **深链** | 新增分层 hash：`#workbench/space/<roomId>`、`#workbench/tasks?project=<id>`、`#workbench/loop/<id>`、`#console/resources/workers/<name>`；旧 `#chat`、`#workers` 等自动映射（客户端 replaceState，不改服务端路由） |
| **快捷入口** | 保留 Ctrl+1..8 节切换；新增 Ctrl+1..3 一级区（工作台/控制台/我的工作台，P1） |

### 5.4 为什么不是「旧路由 301」

前稿声称「所有旧路由 301 到新路径」，但本仓 **没有 per-module 路由**：`src/app` 只有 `/` 与 `/replay/[id]`，section 靠 hash 切换。因此迁移方案改为：

1. **hash 兼容层**（M1 必做）：旧 hash → 新 hash 的客户端映射表（附录 A），`replaceState` 更新，旧书签仍可达；
2. **「经典导航」开关**（默认关，保留一个版本周期）：保持 13 项平铺显示；
3. 若未来要做真正的 URL 路由（可分享到房间/任务），需单独立项（不在本期，见 Q8）。

## 6. 功能需求

> 每个需求给：优先级、可落地性、关键行为规则与验收标准。凡标 🔗 者，必须在里程碑出口前完成「上游契约确认」，否则按降级路径交付并在验收记录中标注。

### 6.1 F1 协作空间（P0）

**目标**：把现有 Matrix Chat 升级为「工作单元」——人、Agent、任务、交付物在同一对话流，且不丢任何现有聊天能力。

| 编号 | 需求 | 优先级 | 可落地性 | 关键行为与验收标准 |
| --- | --- | --- | --- | --- |
| **F1.1** | 空间侧栏与空间模型 | P0 | ⚠️ | 空间 = Matrix 房间 + 可选循环绑定 + 任务上下文。在现有「全部/群组/私聊」分类上增加「空间」语义；保留时间排序、未读角标、宽度记忆。验收：现有房间无损升级；空间项显示绑定循环徽标与运行状态；`#workbench/space/<roomId>` 可直达 |
| **F1.2** | 接力卡（Relay Card） | P0 | ⚠️ | 优先由**项目 workflow 读契约**生成（`tasks_detail` + `dependsOn` + 事件流），不要求新协议：子任务清单、责任 Agent、依赖关系（并行/串行）、各子项实时状态；点开子项可看运行时块（思考/工具调用/产出）。验收：一个 5 节点 DAG 项目在消息流呈现为 1 张卡而非 5 条散消息；状态 15s 内更新；与项目详情双向跳转 |
| **F1.3** | 工件卡三态 | P0 | ⚠️ | 交付物消息化：**草稿 / 待审 / 已放行** 三态徽标（映射任务 `in_progress` / `submitted` / `completed` + 放行记录）；卡片内直达预览、版本、评论入口；若该任务存在编码执行记录（v1.3.1 `coding-runs`），可只读直达。验收：状态变更即时反映并落审计；旧消息按现有渲染降级不受影响 |
| **F1.4** | 人在环指令 | P0 | ⚠️ | @Agent + 引用工件/评论下达修改指令；指令与所在空间、所属项目/循环节点关联并可追溯。**注意**：任务实体由 Manager `projectflow` 创建，Dashboard 本期**不承诺**「@ 即建任务」（见 §8 缺口 G2）；能承诺的是「指令可靠送达 + 关联 + 状态跟踪」。验收：指令历史可查；从指令可跳转到对应任务/工件 |
| **F1.5** | Agent 成员卡 | P0 | ✅ | 头像、名称、心跳状态点（复用权威状态）、技能与工具速览、「直接派活」按钮（进入单聊）。验收：从任意 Agent 头像一步直达会话；技能摘要来自现有技能/MCP 数据面 |
| **F1.6** | 邀请与成员治理 | P1 | 🔗 | 保留邀请收件箱与 `matrix.invite.accept/reject` 审计；「拉 Agent 进空间 / 新建群聊」**依赖上游 Matrix createRoom/invite 代理**（本仓无此 BFF）。降级：提供「复制邀请指引 + 跳转 Matrix 客户端」，并在 UI 明示当前不可直建。验收：接受/拒绝落审计；降级路径无死按钮 |

**兼容性约束**：不改 Matrix 协议；接力卡/工件卡是 Dashboard 侧增量渲染层，未知成分一律降级为现行文本启发式（现有行为不变）。

### 6.2 F2 HITL 干预闭环（P0，v0.9 回填）

**目标**：把「执行中 Agent 主动提问」做成消息内可答复的一等交互，与 F3「审查放行」并列为两条人机回路（过程中被问 / 结果上签字）。

| 编号 | 需求 | 优先级 | 可落地性 | 关键行为与验收标准 |
| --- | --- | --- | --- | --- |
| **F2.1** | 选项式干预卡 | P0 | 🔗（附本地降级） | 卡片结构：问题区 + 单选列表（标题 + 一句话说明 + 序号快捷键）+ Agent 可标记「推荐」并默认选中置顶 + 自由输入（与选项互斥）+ 多问题分页 + 提交按钮禁用规则。**协议缺口**：现有 `confirmation` 块无选项字段（`protocol.ts:59-69`），需扩 `org.agentteams.run` v2（见 §7.3）并推动上游 runtime 发块。降级：渲染为「选项按钮 + 把用户选择转成一条自然语言消息发回房间」，并明确提示「本次选择未回写运行时状态」。验收：提交后卡片只读、显示提交人与时间；仅被请求人/管理员可提交；他人可见不可操作 |
| **F2.2** | 超时与升级 | P0 | ⚠️ | 默认 30 分钟（可配置，按空间或全局）；超时 → `expired` 置灰，任务保持 `blocked`，升级通知该空间全部管理员并落审计。验收：超时行为可复现；配置项有默认值与生效说明 |
| **F2.3** | 聚合收件箱 | P0 | ✅ | 保留现有 HITL Inbox（内存、上限 50），升级为「全部待处理」聚合视图；会话内卡片与收件箱**状态互通**（任一处处理，另一处同步）。验收：两处处理后另一处 1s 内消失；不再出现「已处理仍挂着」 |
| **F2.4** | 回写与审计 | P0 | ⚠️ | 答复内容回写运行时（协议支持时）或作为房间消息（降级）；审计事件 `hitl.request / hitl.answer / hitl.expire`（actor、任务、所选答案、耗时）。验收：审计可检索；断线重连后卡片状态全量校准、不产生重复卡 |

### 6.3 F3 审查闭环（P0）

**目标**：把「审查报告 → 派单 → 复测 → 放行」做成系统闭环，默认终点是**人**。

| 编号 | 需求 | 优先级 | 可落地性 | 关键行为与验收标准 |
| --- | --- | --- | --- | --- |
| **F3.1** | 结构化审查报告卡 | P0 | 🔗（附文本降级） | 报告卡：问题分级（阻断/建议）、位置描述、复现步骤、责任节点归属；可一键折叠为摘要，问题项可单条勾选。来源约定：优先消费 runtime 的结构化报告块（v2 提案 `review.report`）；无结构时按 Markdown 约定模板解析（`## Outcome`、`REVISION_NEEDED` 等现有语义），再降级为普通消息。验收：报告卡可折叠/勾选；降级路径不丢内容 |
| **F3.2** | 修复派单 | P0 | ⚠️ | 人 @ 指令或按循环退回路由生成修复子任务（子任务创建依赖上游，见 §8 缺口 G2）；派单关联原问题项，多轮往返标注「第 N 轮」。验收：问题项与修复记录可互相跳转；轮次清晰可辨 |
| **F3.3** | 复测与放行 | P0 | ⚠️ | 审查通过后向终点人工节点发「放行请求」；放行动作可撤销（生成新版本记录）；放行结果写入**Matrix 房间状态事件**（`com.agentteams.release`，Stateless 安全），并同步工件卡三态。验收：放行后工件卡变「已放行」并落审计；撤销生成新记录而非覆盖 |
| **F3.4** | 人工终审与自动放行 | P0 | ⚠️ | 终点默认人工；「自动放行」需管理员显式开启（按空间），开启后在空间与审计均有醒目标识。验收：默认关闭；开启动作落审计；关闭后立即恢复人工 |

### 6.4 F4 任务中心与看板联动（P0）

| 编号 | 需求 | 优先级 | 可落地性 | 关键行为与验收标准 |
| --- | --- | --- | --- | --- |
| **F4.1** | 看板保留 + 会话维度 | P0 | ✅ | 看板不并入、不降级：保留现有三源合并视图、视图持久化、行内结果；「编码执行」入口归入任务中心（不删不减）；新增「会话」维度（任务卡显示来源空间，点击跳空间并定位到对应卡片/消息）；筛选新增按空间/按执行 Agent/按「待我处理」。验收：双向跳转可用；状态操作与卡片等价且同源同步 |
| **F4.2** | 我的工作台 | P1 | ⚠️ | 聚合：待我审查 / 待我放行 / 我的任务 / @我的消息；一屏处理全部「等我」事项。验收：每类条目可直达上下文 |
| **F4.3** | 通知与未读规则 | P1 | ⚠️ | 优先级：待干预 > 待放行 > 未读消息；顶部横幅聚合「N 条待你处理」；分级（阻断/一般）与免打扰；**不承诺统一 SSE 基建**——现状仅 2 处裸 SSE、无广播/续传（`skills/nacos/events`、`wen-tian/logs`），本期先用 Matrix `/sync` + 轮询实现，SSE 化进 P2。验收：通知点击直达上下文；免打扰时段内不弹 |

### 6.5 F5 循环资产（P1，含 P0 只读子项）

**目标**：把「流程」变成可发布、可复用、可版本化的资产。**执行永远由上游承载**；Dashboard 负责定义、发布、视图、复用。

| 编号 | 需求 | 优先级 | 可落地性 | 关键行为与验收标准 |
| --- | --- | --- | --- | --- |

| **F5.2** | 作者画布 | P1 | ⚠️ + 🔗 | 节点类型：Agent / 人工 / 审查 / 条件 / 起终点；连线表达交接契约（接收什么/交出什么）；自动布局 + 手动微调；100 节点不卡顿。选型：`@xyflow/react` 按需分包（与 3D 图谱同策略，主 bundle 零画布字节）。**执行契约缺口**：画布产物需能被 Controller 消费（loops API，见缺口 G3），否则只能导出 JSON 供 Manager 引用 |

| **F5.5** | 复用与模板库 | P1 | ⚠️ | 已发布循环可被其他空间接入（负责其中一段）；从历史运行「另存为循环」（由项目 workflow 生成草稿，人工确认后发布）；内置 ≥5 模板（产品介绍页生产线 / 代码审查流水线 / 数据分析报告 / 周报生成 / 文档润色）。验收：模板一键实例化为草稿；接入显示来源与版本 |

## 7. 关键对象、状态机与协议

### 7.1 对象模型（新增部分）

| 对象 | 定义 | 存储载体（首版） |
| --- | --- | --- |
| **Space（空间）** | Matrix 房间 + 绑定的循环版本 + 任务上下文 | 房间状态事件 `com.agentteams.space` |
| **RelayEntry（接力项）** | 项目 workflow 中的节点在本空间的投影（责任 Agent、依赖、状态） | 读取 Controller workflow，不落库 |
| **ArtifactCard（工件卡）** | 交付物 + 三态 + 版本 + 评论锚点 | 交付物由 Controller 提供；状态/版本/评论落 Matrix 事件 |
| **Intervention（干预）** | Agent 执行中向人发起的结构化提问 | Matrix 消息（v2 块）+ Dashboard 内存/事件 |
| **ReviewReport（审查报告）** | 轮次、问题列表（分级/位置/复现/责任节点）、结论 | Matrix 消息（结构化块或 Markdown 约定） |
| **Release（放行）** | 对某工件版本的终审确认（可撤销） | 房间状态事件 `com.agentteams.release` |
| **LoopDefinition / LoopVersion / LoopInstance** | 循环定义、版本、运行实例 | Matrix 状态事件 + JSON 导出；实例映射到 Controller 项目 |

> 统一原则：**Controller 是执行与任务状态的事实源；Matrix 是协作事件与资产定义的事实源；Dashboard 不新增服务端持久化域**（Stateless 兼容）。Dashboard 本地仅做缓存加速，丢失可重建。

### 7.2 状态机

- **任务**（沿用上游两套标尺，PRD 只引用前端归一化口径）：`pending → delegated → in-progress → completed`，异常分支 `revision`（需修订）/ `blocked`（阻塞）/ `unknown`；终态：`completed / revision / blocked / cancelled`。前稿的 `queued / done / failed` 命名作废。
- **干预**：`pending → answered`，分支 `expired`（超时）/ `cancelled`（任务已结束）；`answered` 后卡片只读。
- **工件卡**：`draft → pending_review → released`，`released` 可被撤销生成新记录（`revoked`），历史不覆盖。
- **循环版本**：`draft → published → archived`；发布/回滚仅管理员；已发布不可变。
- **审查轮次**：`round 1..N`，每轮报告独立，放行只针对当前轮次的最新版本。

### 7.3 协议扩展提案（`org.agentteams.run` v2，依赖上游）

现状：v1 只有 5 类块（text / thinking / tool_call / confirmation / error），`confirmation` 仅 `tool_name / confirmation_id / parameters / external_files / expires_at`，**无选项、无问题列表、无答案回传约定**（`protocol.ts:59-69`）。因此 F2/F3 的结构化能力必须扩展协议：

| 新增/扩展 | 字段（提案） | 用途 |
| --- | --- | --- |
| `confirmation` v2 | `question`、`options[{id,label,description,recommended}]`、`multi_select`、`questions[]`（多问题分页）、`expires_at`、`answer_schema` | 选项式干预卡 |
| 新块 `review.report` | `round`、`verdict`、`issues[{id,severity,anchor,repro,owner_node}]` | 结构化审查报告 |
| 新块 `relay.plan`（可选） | `subtasks[{id,title,owner,depends_on,status}]` | 接力卡（若上游愿意直发；否则由 workflow 读契约生成） |
| 回传约定 | 用户在房间内的一条结构化消息（`com.agentteams.answer`），携带 `confirmation_id + answer` | 答案回写与审计 |

**兼容承诺**：v2 对旧 Dashboard 表现为未知块 → 文本启发式降级，不丢消息（沿用现有前向兼容语义，`INTERFACES.md:154-159`）。**降级承诺**：上游未实现 v2 时，F2.1 走「本地选项 + 转自然语言消息」，F3.1 走「Markdown 模板解析」，均在 UI 标注能力徽标。

### 7.4 状态一致性与断线恢复

1. **单一事实源**：任务/项目状态以 Controller 为准；协作事件以 Matrix 为准；前端不得自造第二份状态。
2. **原位更新**：同一任务/工件/干预的多条更新折叠为一张卡原位替换，锚定首次出现位置；重连后全量校准，**禁止产生重复卡**（v0.9 规则保留）。
3. **轮询口径**：资源 15s、看板 8s、审计 15s、聊天 workflow 卡 15s（GitHub main：`use-agentteams-*.ts`、`use-task-board.ts:112`、`use-audit-events.ts:79-80`、`chat-workflow-live.ts:12`）；新增卡片复用同一节奏，不新增高频轮询。
4. **降级可见**：任何降级（协议缺失、上游 501、Stateless 限制）必须在 UI 显示可解释徽标，不允许静默失败。

### 8.3 存储选择（Stateless 兼容）

| 数据 | 载体 | 理由 |
| --- | --- | --- |
| 空间绑定、放行记录、循环定义/发布 | **Matrix 房间状态事件**（`com.agentteams.*`） | 随房间权限继承、Stateless 可用、天然审计线索 |

| 任务/项目/实例状态 | **Controller**（不复制） | 唯一事实源 |
| 仪表盘缓存 | 浏览器内存 / localStorage | 可丢弃 |

### 8.4 性能预算

1. 主 bundle 不引入画布/协同字节（`@xyflow/react`、Yjs 全部按需分包，参照 3D 图谱 `next/dynamic` 先例）；
2. 时间线继续虚拟化（react-virtuoso）；接力卡聚合并按需展开；
3. Lighthouse Performance ≥ 现状基线，不允许回退；
4. 画布 100 节点交互流畅（CI 性能预算，P1 阶段加入）。

## 附录 E：术语表

| 术语 | 含义 |
| --- | --- |
| 空间（Space） | 绑定循环与任务上下文的 Matrix 房间（工作单元） |
| 接力（Relay） | 协调 Agent 对任务的拆解、分派与依赖管理，及其在对话流的可视化 |
| 循环（Loop） | 可发布、可复用、带条件退回的 Agent 工作流定义；执行由上游 Controller 承载 |
| 干预（Intervention） | Agent 执行中向人发起的结构化提问及人的答复 |
| 放行（Release） | 人工终点对审查通过成果的最终确认，可撤销 |
| 工件（Artifact） | 任务产出的交付物（网页/文档/图片等）及其卡片化表示 |
| 能力徽标 | UI 上标注「当前上游/部署形态不支持某能力」的可见提示 |
